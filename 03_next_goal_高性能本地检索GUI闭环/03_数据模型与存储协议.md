# 数据模型与存储协议

## 1. Manifest 主模型

Manifest 是下一阶段的根数据模型。

| 字段 | 作用 | 说明 |
|---|---|---|
| `file_pk` | 内部主键 | 单机递增 |
| `stable_file_id` | 稳定文件身份 | Windows 使用 volume + file id；macOS/POSIX 使用 dev + ino + birthtime 辅助 |
| `root_id` | 来源 root | root 可 offline、disabled、rescanning |
| `display_path` | 用户展示路径 | 仅本地显示，不进入公开证据 |
| `canonical_path_hash` | 路径哈希 | 诊断和匹配用 hash，不提交 path |
| `size_bytes` | 文件大小 | quick diff |
| `mtime_ns` | 修改时间 | quick diff |
| `birthtime_ns` | 创建时间 | inode/fileid 回收防护 |
| `quick_fingerprint` | 快速内容指纹 | 判断是否值得解析 |
| `strong_hash` | 强内容哈希 | 按需计算，支持跨路径识别 |
| `file_kind` | 文件类型 | pdf/docx/doc/txt/image/unsupported |
| `parse_state` | 解析状态 | state machine 输入 |
| `text_epoch` | 文本可见 epoch | 文本层搜索可用性 |
| `fulltext_epoch` | 全文索引 epoch | BM25 可用性 |
| `field_epoch` | 字段索引 epoch | filter 可用性 |
| `vector_epoch` | 向量 epoch | semantic 可用性 |
| `snippet_epoch` | snippet sidecar epoch | 结果片段可用性 |
| `last_seen_scan_epoch` | 最近扫描轮次 | 删除和 offline 判断 |
| `tombstone` | 逻辑删除 | 查询默认隐藏 |
| `retry_after_ts` | 重试时间 | 退避 |
| `error_code` | 最近错误码 | diagnostics 和 GUI 展示 |
| `parser_version` | 解析器版本 | 版本变更触发局部重解析 |
| `schema_version` | 存储/索引 schema | breaking change 门槛 |
| `resume_classification` | mixed import 分类状态 | `resume_candidate` / `non_resume` / `needs_review` / `ocr_backlog` / `failed` |
| `classification_reasons` | 分类解释码 | 本地 audit/review 用；公开证据只能输出 reason bucket count |
| `classification_epoch` | 分类版本 | classifier 版本或阈值变化触发局部重分类 |
| `review_state` | 人工复核状态 | 仅本地 backlog，不进入公开证据 |

## 1.1 Mixed Import Classification Record

Mixed import 的分类状态是产品语义合同，不是 parser 成功与否的别名：

| 状态 | 搜索索引 | 本地记录 | 含义 |
|---|---|---|---|
| `resume_candidate` | yes | yes | 多信号高置信简历，可进入 resume search index |
| `non_resume` | no | yes | 明显非简历，保留 audit 记录和聚合原因 |
| `needs_review` | no | yes | 证据不足或冲突，进入本地 review backlog |
| `ocr_backlog` | no | yes | 扫描件/无文本/需 OCR；OCR 前不得判成 `non_resume` |
| `failed` | no | yes | 权限、格式、解析或 IO 失败 |

逐文件 audit/review 记录可在本地存储 `document_id`/fingerprint、原始路径、
扩展名、大小、分类状态、reason codes、分类时间和 parser/OCR 状态。公开报告、
GitHub issue、PR、benchmark summary 和 committed fixtures 不得包含真实路径、
文件名、正文、直接 raw file hash 或私有 labels。

## 2. Mutation Batch

所有导入和增量更新都必须经过 batch 协议：

```text
prepare(batch_id, root_id, manifest_delta, target_epoch)
apply_fulltext(batch_id)
apply_fields(batch_id)
apply_snippet_sidecar(batch_id)
apply_vector(batch_id)
commit(batch_id, visible_epoch, commit_ids)
gc(compactable_before_epoch)
```

## 3. 恢复规则

| 状态 | 恢复动作 |
|---|---|
| prepared 但未 apply | 重放 batch |
| fulltext 已 apply 但 SQLite 未 commit | 用 `batch_id` 幂等对账 |
| SQLite 已 commit 但派生层缺失 | 从 batch log 补写派生层 |
| vector 失败 | semantic partial，keyword/field 仍可用 |
| snippet sidecar 缺失 | 返回无 snippet 或短 fallback，不阻塞搜索 |
| tombstone 长期存在 | 等旧 reader drain 后物理清理 |

## 4. Visible Epoch

Visible epoch 是 GUI、CLI、daemon 和 Codex 验证共同理解系统状态的唯一版本点。

每个 response 至少能说明：

1. `visible_epoch`
2. `fulltext_epoch`
3. `field_epoch`
4. `vector_epoch`
5. `snippet_epoch`
6. `partial_reason`

## 5. Sidecar

正文和长 snippet 不进入 Tantivy 热路径 STORED 大字段。

| Sidecar | 内容 | 访问方式 |
|---|---|---|
| snippet sidecar | top result 片段、短摘要、highlight window | doc id -> pointer -> chunk |
| body sidecar | 规范化正文和 section chunk | detail 或 snippet fallback 才读 |
| vector sidecar | embedding payload、ANN snapshot、tombstone | semantic layer 读取 |

写入采用同卷 temp + 校验 + atomic replace/rename。

## 6. Source-root and path-truth identity contract

Schema v31 hard-cuts business identity to an authorized root plus normalized
relative path:

| layer | field | contract |
|---|---|---|
| root identity | `SourceRootId` | stable opaque id owned only by meta-store; paths never cross IPC or evidence |
| occurrence identity | `{root_id, normalized_relative_path}` | the exact business identity of one source occurrence |
| revision identity | `SourceRevision` | immutable content revision for that occurrence |
| reusable work | `content_hash` | only a cache key for parser/OCR/embedding reuse, never cross-path business identity |

Rename and truth handling:

1. rename or move removes the old occurrence and imports a new occurrence;
2. same-path content replacement creates a new revision and atomically replaces
   the active result;
3. move into another authorized root is a new source identity;
4. a complete, error-free, in-budget scan may remove missing occurrences;
5. offline, permission-denied or partial scans retain the last trusted
   projection and report unknown completeness;
6. a zero-change scan creates no new resume version or visible epoch.

## 12. S807 v27 immutable publication hard cut

Schema v27 replaces mutable resume rows with three explicit facts:

1. `Document` is stable source identity and reachability only.
2. `SourceRevision` is content-addressed source evidence; `ResumeVersion` is an
   insert-once value derived from document identity, source/content revision,
   normalized-text hash, parser version, and schema version. The same version id
   with different bytes or derived facts is an invariant failure.
3. `ActiveSearchProjection(document_id -> resume_version_id)` is the sole search
   admission fact. Classification, mentions, candidate linkage, full-text rows,
   and vector rows are version-bound; mutable visibility is retired.

Staged revisions and derived data are inaccessible to query/detail. Publication
first validates complete full-text and vector snapshots, then one SQLite CAS
transaction swaps the projection, ingest terminal state, index generation,
visible epoch, and publication journal. A query lease pins immutable readers,
metadata read transaction, generation, and epoch so a request is all-old or
all-new. v26 migration is copy-on-write: preserve only authorized root/source/
document identity, invalidate all legacy derived facts and index artifacts, and
remain `repairing` until a validated v27 publication exists. No dual reader,
legacy alias, synthetic version backfill, or latest-row fallback is allowed.

## 13. 2026-07-21 current-v29 owner-open hard cut

Production metadata admission is exact-schema only. An existing store is
accepted only when its manifest is schema `29`, its existing encryption key can
be read without mutation, and integrity/fingerprint checks pass. That path may
open and preserve business data, active projection, visible epoch, and artifact
digests; it may not create a key, migrate a predecessor, rewrite a manifest, or
clean up predecessor files.

A fresh v29 store may be created only when manifest, key, legacy database, and
old migration authority are all absent. Creation happens in a temporary empty
store, runs the current schema initializer and full validation, syncs, and then
publishes atomically. Historical DDL is an implementation detail behind this
schema-zero initializer, never a production migration API.

Schemas v27, v28, unknown authorities, missing keys, fingerprint mismatch, and
integrity failure return typed blockers and leave all existing bytes unchanged.
There is no v1/v2 reader, v28-to-v29 migrator, dual write, compatibility flag,
automatic re-import, or destructive cleanup. This section supersedes every
older runtime-migration clause while retaining the v29 immutable publication
and `{doc_id, version_id, visible_epoch}` selection semantics.

## 14. 2026-07-24 schema v30-v33 feature-train hard cut

This section supersedes section 13's v29-only admission rule. Production accepts
exact current schema v33 or continuously migrates v29 through every registered
adjacent step to v33 in same-key encrypted COW staging. v27, v28, future,
missing-key and damaged authorities still fail closed without changing source
ciphertext. One encrypted predecessor is retained until privacy deletion
requires its destruction.

- v30 owns manifest v2, migration history and bounded recovery receipt.
- v31 owns `source_root`, path-truth occurrences, immutable occurrence revision
  history and scan snapshots.
- v32 owns durable root-deletion receipts and the complete set of exclusive
  document revisions/content hashes needed for crash-safe privacy cleanup.
- v33 owns persistent PDFium parser reprocessing.

全新空库的首次发布不复用迁移 receipt，而使用独立的
`resume-ir.metadata-initialization-receipt.v1`。该 receipt 在创建加密 staging
之前发布；只有 v33 结构、完整性和 store identity 全部验证并同步后，才按
`ready -> key -> manifest` 顺序发布 authority。崩溃恢复只能继续发布同一个已验证
target，或精确删除该 receipt 命名的未发布 staging、target 和新 key；不得猜测、
扫描或清理其他文件。

Root deletion first fences scan/import/OCR/PDF reprocessing, atomically removes
the root's search projection, then purges occurrences, all historical derived
facts, unreferenced OCR/embedding/artifacts and any retained migration
predecessor. The root remains visible as `deleting` until one final transaction
proves zero residuals, removes root authority and completes the receipt. Source
files are never deleted.

## 15. 2026-08-05 schema v36 deletion-attempt evidence

Schema v36 adds exactly one `source_root_deletion_attempt_evidence` row for each
durable deletion receipt. The receipt remains the deletion authority; the new
row is observation only and is deleted by the receipt foreign-key cascade. It
stores a saturating JavaScript-safe `attempt_count`, `last_attempt_at`, and one
all-null or all-present tuple of `last_error_phase`, fixed `last_error_code`, and
`last_error_at`. Saturation must never reject or delay another deletion attempt.

The v35-to-v36 migration backfills existing receipts with zero attempts and no
invented error. Each worker attempt clears the prior error tuple before running;
a failed attempt records the typed deletion cause produced at the failure site.
This evidence does not own retry timing, phase transitions, reconciliation,
cleanup order, or recovery policy.

## 16. 2026-08-05 schema v37 deletion checkpoint protocol

Schema v37 adds one `checkpoint_protocol_version` integer to the authoritative
`source_root_deletion` receipt. The closed values are `1` for a legacy or
unattested snapshot and `2` for a snapshot that satisfies checkpoint invariant
v2 at the time of attestation. The value is an upgradable checkpoint
attestation, not immutable creation provenance and not a fence against later
ownership changes.

The v36-to-v37 migration defaults every existing receipt fail-closed to `1` and
preserves its phase, metadata, document snapshot and attempt evidence. The sole
new-receipt writer explicitly writes `2` in its existing `Immediate`
transaction; omitting the column can never imply the current invariant. A
future `1` to `2` transition is valid only in the same transaction that safely
reconciles the receipt snapshot. Schema v37 itself does not read the marker to
change retry, phase, cleanup or recovery behavior and does not reconcile any
historical receipt.

## 17. 2026-08-06 schema v38 source-root revocation epoch

Schema v38 adds bounded SQLite-integer `revocation_epoch` to each source root and immutable captured `root_revocation_epoch` to each scan snapshot.
The legal domain is `0..=9007199254740991`; saturation, another storage class or a CAS miss fails closed, and both writers capture explicitly while default zero serves only legacy backfill.
The v37-to-v38 COW migration assigns epoch `1` to every extant root with any valid deletion receipt, including `failed`; roots without receipt history and legacy scans remain `0`.
Unknown phases or impossible receipt/root pairs abort publication; deletion begin is the sole runtime writer and bumps in the existing `Immediate` transaction.
Existing scan coalescing precedence remains, and only a new task/scope/snapshot commit performs final typed admission.
Admission uses persisted import-task identity to prove task, scope, snapshot, root paths and captured epoch in one read; caller-supplied epoch is not authority.
This is foundation only: immutable-ingest and occurrence commits are not wired to the fence, and Publishing/Purging reconciliation is unchanged.
